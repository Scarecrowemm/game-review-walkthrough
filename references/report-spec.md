# 报告结构与渲染规范

## 两份文档的分工

| 文档 | 文件名 | 读者 | 首屏必须出现 |
|------|--------|------|--------------|
| 评测 | `<游戏名>-评测.html` | 还没决定要不要玩的人 | 证据基础、利益声明、加权总分与定级 |
| 攻略 | `<游戏名>-攻略.html` | 已经握着手机/手柄卡在某处的人 | 覆盖范围、四层导航、证据基础 |

**不合并。** 评测读者关心"值不值"，攻略读者关心"怎么过"。合并后攻略会被迫往上滚动十几屏才能找到第一个可用步骤。

## 渲染流程

```bash
# 数据定稿前反复快速校验
python scripts/build_report.py report-data.json --check

# 正式出报告
python scripts/build_report.py report-data.json --out ./out
```

脚本行为：

1. 校验 schema 与证据字段（规则见 `evidence-protocol.md` 第四节）。
2. 校验权重与 rubric 一致、权重和为 1.00。
3. 计算加权总分 → **先四舍五入到 1 位，再据此判级**（避免"显示 7.0 却定级尚可"这类浮点自相矛盾），随后按 `evidence_base` 封顶。
4. 渲染两份 HTML，残留占位符会被清除；样式由 `assets/report.css` 内联注入，产出文件自包含、可离线打开。
5. 校验失败时一次性列出全部错误并非零退出。

## 配图渲染

三处入口，逻辑统一在 `render_figures()`：

1. **声明式配图** — 数据里 `images` 数组的每一项都渲染成一张 `<figure>`。
2. **自动示意图** — 有 `phases` 但没声明阶段示意图 → 自动补一张血量进度条；有 A 层章节 → 自动补一张章节推进骨架。**不需要用户准备素材**。
3. **待补图占位** — 声明了 `path` 但文件不存在 → 渲染成虚线占位框，写明所需图的类型、路径与 `how_to_get`。报告因此同时是一份采图清单。

图片落盘方式由 `--image-mode` 控制：

| 模式 | 行为 | 适用 |
|------|------|------|
| `copy`（默认） | 复制到 `<out>/assets/`，报告用相对路径引用 | 本地查看、存档。分享时要连目录一起打包 |
| `inline` | 转 base64 内嵌 | 发给别人、发聊天窗口，单文件即可用 |
| `link` | 引用原始绝对路径 | 图片已在固定位置、不想复制副本时 |

自动示意图的两条设计红线（改代码时不要破坏）：

- 阶段进度条**只按 `hp_range` 等比例绘制**，不标 BOSS 站位、不标场地坐标。没有数据支撑的空间信息一律不画。
- 章节骨架**等距排布**，不按时长比例，图注明确写出这一点，避免读者误读为"这章更长"。

### 已踩过的两个坑（真实项目复盘，别再踩）

1. **整条血条重置型 BOSS 画不出阶段条。** 若某场 BOSS 是「打空一条血→回满→第二条血」（如《Hades》的冥王），把 `hp_range` 写成 `100%-0%` + `100%-0%` 会让两段色块完全重叠、标签叠在一起，图不可读。处置：这类 BOSS 的 `hp_range` **故意不写数字**（例如「第一条血，满血打到见底」），`phase_timeline_svg()` 解析不到数字会返回空串，报告自动不渲染该图——留空优于画错。血量数字改在 `pattern` 字段里用文字说明。
2. **`game.materials` 目前不参与渲染。** 它只被 `check_game()` 用来判断「有没有可核素材」从而决定是否发警告，报告里不会出现这个字段。若想让读者看到一手证据清单（成就缓存、存档、游戏自有脚本等），必须写进正文（例如 `review.dimensions[].evidence[].note`）或 `completion`，不能只填 `materials` 就以为展示过了。

### 另注：无截图场景下的警告噪音

`A_main_route` 与 `C_bosses` 的每条目在无 `images` 时都会各发一条警告。当用户明确选择「不做截图、走存档+成就证据」时，这些警告会一次性出现十几条但**不是错误**，渲染照常进行。可通过给该条目声明 `kind=diagram` + `is_illustration=true` + `diagram_type=phase_timeline` 抑制（前提是 `hp_range` 可解析，见上面第 1 条）。

## 视觉规范

- **浅色主题**：白底卡片、深色文字。报告是要被打印和投影的，深色主题在这两个场景都会翻车。
- **分数配色**：≥8 绿、6-7 黄、<6 红，通过卡片左侧色条表达，不用大块色底。颜色只用于传达状态，不用于装饰。
- **证据可视化**：E2 灰色徽标「素材」、E4 橙色「推断」、E5 红色「未验证」，E1/E3 不加徽标（有证据是常态，不需要庆祝）。读者应该能一眼扫出哪些结论是硬的。
- **雷达图**：纯内联 SVG，无外部依赖，无网络请求。写文件时必须能离线打开。
- **响应式断点** 720px，窄屏下锚点双列降为单列，BOSS 阶段表横向滚动。读者很可能在手机上一边玩一边看。
- **打印样式**：去掉阴影、避免卡片跨页断裂。存档用、群里发用。

## 模板占位符

模板文件在 `assets/`，占位符由脚本填充，残留的会被自动清除。**不要手工编辑生成后的 HTML**——下次渲染会覆盖。

### review-template.html

| 占位符 | 内容 |
|--------|------|
| `{{CSS}}` | `report.css` 全文 |
| `{{GAME_TITLE}}` / `{{TITLE_EN}}` | 游戏名（中/英） |
| `{{GAME_META}}` | 平台 ｜ 版本 ｜ 语言 ｜ 评测日 |
| `{{BANNER}}` | 证据基础 + 利益声明 + 完成度 + 警告列表 |
| `{{COVER}}` | `game.images` 的封面图组 |
| `{{SCORE_BLOCK}}` | 加权总分与定级（证据不足时显示「不出总分」） |
| `{{RADAR}}` | 七维雷达 SVG |
| `{{SUMMARY}}` | 总评 |
| `{{DIMENSION_CARDS}}` | 七张维度卡：分数、权重、贡献分、加减分锚点、证据 |
| `{{PROS}}` / `{{CONS}}` | 优点 / 缺点列表 |
| `{{SERIES_NOTE}}` | 系列对比（明确标注不计入总分；无内容时整段消失） |
| `{{BIAS_AUDIT}}` | 公正性自查表行 |
| `{{SOURCES}}` | 来源清单 |
| `{{GENERATED_AT}}` | 生成时间 |

### walkthrough-template.html

| 占位符 | 内容 |
|--------|------|
| `{{CSS}}` | 同上 |
| `{{GAME_TITLE}}` / `{{GAME_META}}` | 同上 |
| `{{BANNER}}` | 覆盖范围 + 证据基础 |
| `{{COVER}}` | `game.images` 的封面图组 |
| `{{NAV}}` | 四层锚点导航 |
| `{{LAYER_A}}` … `{{LAYER_D}}` | 四个层区块（含层标题与条目渲染） |
| `{{UNVERIFIED}}` | 待验证清单，按 priority 着色 |
| `{{SOURCES}}` / `{{GENERATED_AT}}` | 同上 |

## 需要改样式时

改 `assets/report.css`，不要改模板里的内联样式，也不要在生成后的 HTML 上打补丁。改完重新跑脚本即可，两份报告会同时生效。

新增字段时：先在 `sample-report-data.json` 里补示例，再改 `build_report.py` 的 `render_*` 函数与模板占位符，最后跑一次样例确认通过校验。
